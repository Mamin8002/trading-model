# Данные: формат CSV, время, таймфреймы и проверки

Проектные основания: [research.md](research.md) (факты API, Q1–Q9), [architecture.md](architecture.md) §3, [decisions.md](decisions.md) D1–D3.

## 1. Формат входного CSV

```
datetime,open,high,low,close,volume
2021-01-04 10:00:00,274.67,274.67,274.67,274.67,123460
2021-01-04 10:01:00,274.67,274.67,273.1,274.0,863220
```

- Колонки — **ровно** этот набор (порядок колонок не важен); лишние и недостающие колонки — ошибка.
- `datetime` — `YYYY-MM-DD HH:MM:SS` (naive, в таймзоне `data.source_timezone` конфига,
  по умолчанию `Europe/Moscow`) либо ISO-8601 со смещением (`...T10:00:00+03:00`, `...Z`).
- `open/high/low/close` — десятичные числа **с точкой** (запятая-разделитель и разделители
  тысяч отклоняются), строго положительные, конечные.
- `volume` — целое неотрицательное число (штуки). Дробные объёмы отклоняются.
- Пустые строки пропускаются; файл без данных (пустой/только заголовок) — ошибка `E_EMPTY_FILE`.
- Кодировка UTF-8 (BOM допустим).

### Что проверяется (ошибки — загрузка отклоняется)

| Код | Проверка |
|---|---|
| E_EMPTY_FILE | файл пуст / нет валидных строк / не найден |
| E_HEADER_MISSING_COLS, E_HEADER_UNKNOWN_COLS | набор колонок не совпадает с требуемым |
| E_DATETIME_PARSE | метка времени не разбирается |
| E_NUMBER_PARSE, E_PRICE_INVALID | нечисловое значение; цена ≤ 0 |
| E_VOLUME_INVALID | объём не целое неотрицательное |
| E_DUPLICATE_TS | дубликаты меток времени |
| E_UNSORTED | строки не упорядочены по времени (данные НЕ сортируются молча — исправьте источник) |
| E_OHLC | нарушены соотношения: требуется `low ≤ open/close ≤ high`, `low ≤ high` |
| E_OFF_GRID | метка не кратна шагу таймфрейма (например 10:03 для 5m) |

### Что отмечается предупреждениями (загрузка succeeds, факт виден в отчёте)

| Код | Смысл |
|---|---|
| W_GAP | пропуски баров (против календаря сессий, если задан, иначе против равномерной сетки). Пропуски **не заполняются** — никакие синтетические бары не создаются |
| W_ZERO_VOLUME | нулевой объём бара |
| W_OUT_OF_SESSION | бар вне настроенных сессионных окон |

## 2. Время: семантика метки и таймзона

- **Семантика метки задаётся явно** в конфиге: `data.timestamp_semantics: bar_open | bar_close`.
  Значения по умолчанию «на глаз» нет: в референсном проекте WISEPLAT скрипт генерации
  и опубликованные CSV противоречат друг другу (research Q3), поэтому семантику нужно
  подтвердить по вашим данным. Как проверить: сравните время первого/последнего бара
  торговой сессии в файле с фактическими границами сессии инструмента
  (например, если вечерняя сессия заканчивается в 23:50 и последний бар помечен 23:50 —
  это, вероятно, `bar_close`; если 23:49 — `bar_open`).
- Внутреннее представление всегда: **UTC, tz-aware, bar_open**. Нормализация:
  naive-метки локализуются в `source_timezone` → UTC; при `bar_close` из метки
  вычитается длительность таймфрейма.
- Таймзона источника — `data.source_timezone` (IANA-имя, например `Europe/Moscow`).
  На Windows для IANA-таймзон требуется пакет `tzdata` — он объявлен в зависимостях.
- **Свечи Finam API**: документация не фиксирует, является ли `timestamp` началом или
  концом интервала (research Q3). Адаптер требует ЯВНО указать
  `finam.bar_timestamp_semantics` (в конфиге) или `--bar-timestamp-semantics` (в CLI);
  при `null` нормализация отклоняется. Проверить эмпирически можно необязательной
  командой `smoke_readonly` (раздел 6): сравните выведенное время первого/последнего
  бара с расписанием торгов.

## 3. Таймфреймы и агрегация

Поддерживаются: **1m, 5m, 10m, 15m, 1h** (enum `Timeframe`, `data/bar.py`).

- **10m в Finam API не существует** (в документированном enum `TimeFrame` нет M10 —
  research §2.3). Поэтому 10m всегда строится локально ресэмплингом из более мелкого
  базового ТФ (`timeframes."10m".base_timeframe: "5m"` — обязательно в конфиге;
  решение D3).
- Правила агрегации OHLCV (единый модуль `data/resampler.py` для TEST и будущего LIVE):
  - open = open **первой** свечи группы; high = **максимум** high; low = **минимум** low;
    close = close **последней** свечи; volume = **сумма** объёмов;
  - группы — по календарной сетке целевого ТФ (для целочасовых смещений зон сетка UTC
    и локальная совпадают);
  - **неполный интервал никогда не выдаётся за полный**:
    - хвост данных (интервал ещё не закрыт исходными барами) возвращается отдельно как
      `pending` с `is_final=False` и не входит в список полных баров;
    - интервал с пропусками внутри (покрытие < ожидаемого) по умолчанию НЕ выпускается
      и фиксируется в `issues` (`coverage_incomplete`, expected/found); опция
      `allow_incomplete=True` выпускает его с явной пометкой `is_final=False`;
    - пустые интервалы не фабрикуются (`no_source_bars`);
  - ожидаемое покрытие считается по календарю сессий (если задан), иначе по равномерной
    сетке;
  - нефинальные исходные бары (незакрытые свечи потока) в агрегации не участвуют
    (`non_final_skipped`) — решения принимаются только по завершённым свечам (D9).
- Результат агрегации помечается `source=BarSource.DERIVED` (расширение enum из
  architecture §3.2 — зафиксировано здесь и внесено в architecture.md).

### Торговые сессии

Календарь сессий настраивается в конфиге (`sessions:` — дни недели и окна `HH:MM`
в локальном времени биржи; окна в пределах одних суток). Точные расписания MOEX
меняются и зависят от режима торгов — **в конфиге задаются ваши фактические окна**,
в LIVE-фазе они будут сверяться с документированным методом `Schedule`. Без календаря
пропуски считаются по равномерной сетке (разрывы сессий выглядят как W_GAP — это
предупреждения, не ошибки).

## 4. Конфигурация

Схема: `src/tradebot/config/schema.py` (pydantic, `extra="forbid"` — опечатки
отклоняются). Примеры: `configs/example.yaml` (шаблон под реальные данные),
`configs/demo.yaml` (демо-проверки на синтетическом файле).

Обязательные явные значения (ничего не подбирается молча):
- `data.timestamp_semantics` — семантика метки CSV;
- для каждого таймфрейма — `lookback_bars` (глубина истории признаков) и
  `horizon_bars` (горизонт прогноза), оба ≥ 1;
- для `10m` — `base_timeframe` (`"5m"` или `"1m"`).

Секреты в конфиге запрещены: хранятся только **имена** переменных окружения
(`finam.secret_env_var`, `finam.account_id_env_var`).

Хэш конфига (`config_hash`) детерминирован и предназначен для связывания артефактов
(датасеты/модели/отчёты) с настройками (architecture §3.2).

## 5. Демонстрационные данные

`data/demo/DEMO_M1.csv` — **СИНТЕТИЧЕСКИЕ демонстрационные данные**, не рыночные:
120 минутных баров за четверг 2024-01-04 10:00–11:59 Europe/Moscow, детерминированный
шаблон `open=100+0.01·i, high=open+0.05, low=open−0.05, close=open+0.02, volume=1000+10·i`.
Символ `DEMO@DEMO` в `configs/demo.yaml` выбран намеренно, чтобы демо-данные нельзя
было спутать с реальным инструментом.

## 6. Запуск проверок

Все команды — из корня репозитория. Установка (PowerShell):

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

### Офлайн-проверка данных (сеть и секреты не нужны)

```powershell
# ручная проверка фазы 0-2 (конфиг, CSV, агрегация, Finam-адаптер на подменном транспорте)
python scripts\manual_checks\check_phase_02_data.py

# юнит-тесты
python -m pytest -q

# валидация демо-данных через CLI (+ агрегация в 10m)
python -m tradebot.cli.validate_data --config configs\demo.yaml --resample 10m

# валидация вашего CSV (семантику метки укажите явно)
python -m tradebot.cli.validate_data --csv data\raw\SBER_M1.csv --timeframe 1m --timestamp-semantics bar_open
```

Ожидаемый вывод ручного сценария — 24 строки `PASS` и итог `RESULT: PASS (24/24 checks)`,
код возврата 0. При любой неудаче — `FAIL` по конкретной проверке, итог
`RESULT: FAIL (n/24)`, код возврата 1.

### Необязательная read-only проверка РЕАЛЬНОГО Finam API

**Потребует ваши учётные данные** (secret_key выпускается в разделе «Токены» портала
Finam; показывается один раз). Автоматически не запускается; заявок не отправляет
(торговые операции в проекте не реализованы):

```powershell
$env:TRADE_API_SECRET = "<ваш secret_key>"          # только в текущей сессии терминала
python -m tradebot.cli.smoke_readonly --symbol SBER@MISX --timeframe 5m --hours 24 --bar-timestamp-semantics bar_open
```

Команда выполняет только документированные GET/POST-чтения: аутентификация,
детали токена (печатается число счетов и readonly — **без идентификаторов**),
метаданные инструмента, торговые параметры (если задан `FINAM_ACCOUNT_ID`),
история свечей, снимок котировки, снимок стакана. Секреты маскируются в ошибках
и логах (`***SECRET_KEY***`, `***ACCESS_KEY***`).

Альтернатива через файл `.env` (игнорируется git-ом; скопируйте `.env.example`):

```powershell
Copy-Item .env.example .env   # затем заполните .env своими значениями
python -m tradebot.cli.smoke_readonly --env-file .env --symbol SBER@MISX --timeframe 5m --hours 24 --bar-timestamp-semantics bar_open
```

### Если проверка не прошла — что прислать

1. полный вывод `python scripts\manual_checks\check_phase_02_data.py` (без обрезки);
2. вывод `python --version` и `python -m pip show tradebot pydantic PyYAML`;
3. ОС/версию PowerShell;
4. для ошибок с вашими CSV — вывод `python -m tradebot.cli.validate_data --csv <файл> --timeframe <ТФ> --timestamp-semantics <...>`
   (первые ~50 строк отчёта достаточно); **сами CSV и секреты не присылайте**;
5. если падает `smoke_readonly` — текст ошибки (секреты в нём замаскированы автоматически).

## 7. Ограничения адаптера Finam (зафиксировано, не угадано)

- Реализованы только подтверждённые документацией read-only методы: auth-поток,
  `bars`, `quotes/latest`, `orderbook` (снимок), `assets/{symbol}`, `assets/{symbol}/params`.
  `Clock/Schedule/Usage/Exchanges/AllAssets` подтверждены swagger-ом по путям, но их
  схемы ответов в этой фазе не сверялись — будут добавлены на этапе L1 (roadmap).
- Потоковые подписки (WS `wss://api.finam.ru/ws` / gRPC-стримы) документированы,
  интерфейс `StreamSource` определён, реализация — этап L2 (roadmap); официальный
  Python SDK `finam-sdk` (gRPC) подключается там же (decisions D7).
- Стакан: формат снимка подтверждён (rows: price, buy_size|sell_size, action, mpid,
  timestamp); **гарантированная глубина не документирована** (research Q4) — код
  возвращает фактическое число уровней и не предполагает фиксированной глубины.
- Лимиты: клиентский limiter ≤ 200 запросов/мин **на метод**; 429 → ожидание окна
  и один повтор; GET 500/503/504 и транспортные сбои → backoff 1→2→4 с + jitter;
  400/404 не повторяются (таблица повторов — research §2.8).
- Выставление/отмена заявок не реализованы нигде в коде (запрет задачи этой фазы);
  гигиена-тесты блокируют появление торговых эндпоинтов в исходниках.
