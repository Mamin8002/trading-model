# Roadmap: этапы реализации (без кода на текущем этапе)

Дата: 2026-10-21. Каждый этап — небольшой, с проверяемым результатом (критерии приёмки), файлами и рисками.
Этап считается принятым, только если выполнены ВСЕ критерии приёмки; артефакты этапа (отчёты, фикстуры, тесты) коммитятся.
Ссылки: факты API — [research.md](research.md), модули — [architecture.md](architecture.md), обоснования — [decisions.md](decisions.md).

Обозначения блоков: **D** — данные, **F** — признаки, **M** — ML, **B** — бэктест/стратегия, **L** — LIVE/API.

---

## Этап 0. Каркас проекта и качество

- **Цель**: пустой, но проверяемый скелет: структура каталогов (architecture.md §2), CI (ruff, mypy, pytest), pre-commit, pyproject с extras (`ml`, `live`), README, .gitignore (.env, data/, артефакты), configs/base.yaml + pydantic-схема конфигурации (пока без бизнес-логики).
- **Файлы**: `pyproject.toml`, `.gitignore`, `README.md`, `configs/base.yaml`, `configs/schema/` (pydantic-модели), `src/tradebot/config/*`, `tests/test_config_schema.py`, CI-workflow.
- **Риски**: преждевременное усложнение схемы конфига. Митигация: схема покрывает только поля из architecture.md §3.4.
- **Приёмка**:
  1. `pip install -e .[dev]` и прогон pytest/ruff/mypy — зелёные в CI;
  2. невалидный YAML (лишнее поле, неверный тип, неизвестный таймфрейм) отклоняется с понятной ошибкой;
  3. хэш конфига детерминирован (одинаковый YAML → одинаковый хэш);
  4. в репозитории нет секретов (проверка gitleaks/pre-commit).

## Этап D1. Контракт данных: загрузка и валидация CSV, детектор семантики метки

- **Цель**: `data/` модуль: тип `Bar`, загрузчик CSV `datetime,open,high,low,close,volume`, валидатор (схема, монотонность, уникальность, OHLC-инварианты, объёмы, пропуски против календаря), детектор `timestamp_semantics` (bar_open|bar_close) и таймзоны, нормализация к UTC bar_open, parquet-хранилище + манифесты. Закрывает Q3 по пользовательским CSV.
- **Файлы**: `src/tradebot/data/{bar,csv_loader,validator,bar_store,calendar}.py`, `src/tradebot/cli/validate_data.py`, `tests/data/` (синтетические фикстуры: сдвиг метки на 1 бар, дубли, разрывы сессий, аукционы), отчёт-фикстура по CSV пользователя.
- **Риски**: неоднозначная семантика метки в реальных файлах (прецедент WISEPLAT, S9e/S9h); разные таймзоны выгрузок. Митигация: детектор + явное подтверждение в конфиге; при спорных данных — ручной просмотр граничных сессий.
- **Приёмка**:
  1. валидатор на синтетических «грязных» фикстурах выдаёт точный список дефектов (тип, строка), ничего не чинит молча;
  2. детектор семантики на эталонной фикстуре (известная сессия MOEX: первый/последний бар дня) определяет bar_open/bar_close верно;
  3. реальные CSV пользователя проходят загрузку, отчёт сохранён (`reports/data_validation_*.md`), значение `timestamp_semantics` зафиксировано в конфиге;
  4. round-trip CSV → parquet → Bar без потерь (тест).

## Этап D2. Ресэмплинг и сверка источников

- **Цель**: `Resampler` (5m→10m, опция 1m→10m; open/high/low/close/volume-правила; только полные группы; pending-хвост), `SessionCalendar` (границы сессий/клиринга — не фабриковать бары вне сессий); утилита сверки CSV 10m пользователя против ресэмплинга из CSV 5m; тест эквивалентности «ресэмплинг из потока» ≡ «ресэмплинг из истории» (задел под D3/L2).
- **Файлы**: `src/tradebot/data/resampler.py`, расширение `calendar.py`, `tests/data/test_resampler.py` (фикстуры: стык сессий, вечерний клиринг, пропуск бара, неполный хвост), `reports/resample_equivalence_*.md`.
- **Риски**: стыки сессий и аукционы дают нестандартные границы 10m-баров (Q5); пропущенные 5m-бары ломают пары. Митигация: правила группировки по календарной сетке + явная политика пропусков (пропустить группу / интерполировать — запрещено по умолчанию), фикстуры на реальных стыках.
- **Приёмка**:
  1. на синтетике ресэмплинг точен (включая volume=sum, high=max, low=min);
  2. неполный хвост никогда не попадает в выход (тест-свойство);
  3. CSV 10m пользователя и 10m из ресэмплинга 5m совпадают ≥99.9% баров на пересечении окон; расхождения объяснены в отчёте (сессии/пропуски);
  4. задокументировано поведение на стыке утренней/основной/вечерней сессий.

## Этап F1. Библиотека признаков (набор v1)

- **Цель**: `features/`: причинные индикаторы (returns, SMA/EMA, RSI, ATR, rolling std, объёмные, позиционные, внутридневные ordinal) и `FeatureBuilder`: окно `lookback_bars` на закрытии бара → вектор признаков; манифест колонок + версия набора (`features.set: v1`).
- **Файлы**: `src/tradebot/features/{indicators,builder,manifest}.py`, `tests/features/test_indicators.py` (численные эталоны против pandas-референсов), golden-фикстура «CSV → матрица признаков».
- **Риски**: «центрированные»/заглядывающие индикаторы (shift-ошибки); NaN-прогрев окна. Митигация: единое правило — значение для решения в t использует бары с ts_open+tf ≤ t; прогрев = явный warmup-период без сигналов.
- **Приёмка**:
  1. все индикаторы совпадают с референсными значениями на фикстурах (включая границы окон);
  2. FeatureBuilder выдаёт стабильный порядок колонок и манифест;
  3. warmup-период (первые lookback баров) помечается, признаков «из будущего» нет (проверяется этапом F2).

## Этап F2. Тест причинности (защита от утечек, часть 1)

- **Цель**: property-based тесты причинности: (а) возмущение любого бара после t не меняет вектор признаков в t; (б) удаление хвоста истории не меняет признаки до t; (в) дедупликация по (symbol, tf, ts_open).
- **Файлы**: `tests/features/test_causality_props.py` (hypothesis), линтер-правило/архитектурный тест: `strategy`, `live`, `features` не импортируют `labels`.
- **Риски**: ложные срабатывания на плавающей точке. Митигация: сравнение с допуском, фиксированные seed-фикстуры.
- **Приёмка**: 1000+ сгенерированных возмущений — ноль нарушений причинности; архитектурный тест зелёный.

## Этап M1. Метки, датасет, сплиты, leakage-аудит

- **Цель**: `labels/` (fwd_return через H баров, нейтральная полоса band из конфига; альтернативы-заглушки: регрессия), `ml/dataset.py` (сборка X/y с манифестом), `ml/splits.py` (PurgedWalkForwardSplit с embargo ≥ horizon_bars), leakage-аудит: отчёт «random-split vs walk-forward» на заведомо синтетическом leaky-признаке (должен детектироваться) и на реальных данных.
- **Файлы**: `src/tradebot/labels/*`, `src/tradebot/ml/{dataset,splits,audit}.py`, `tests/ml/test_splits.py` (нет пересечения train/test по времени; embargo соблюдён), `reports/leakage_audit_*.md`.
- **Риски**: перекрытие меток между фолдами; бан-дисбаланс классов при узкой полосе. Митигация: embargo обязателен; статистика классов в манифесте датасета.
- **Приёмка**:
  1. тесты сплитов зелёные (включая границу embargo=horizon);
  2. аудит ловит подброшенный leaky-признак (AUC random-split ≈ 1.0 vs walk-forward ≈ 0.5) — демонстрация работоспособности аудита;
  3. датасет по реальным CSV собран, манифест (хэш конфига, окна, число строк, баланс классов) сохранён;
  4. per-timeframe конфигурации (5m, 10m, 15m, 1h, 1m) собираются без ошибок при своих lookback/horizon.

## Этап M2. Обучение: LightGBM-базейн, сравнение с CatBoost и sanity-базейнами

- **Цель**: `ml/train.py` + `ml/registry.py` (артефакт + манифест: конфиг, признаки, сплиты, метрики, seed, версии библиотек); обучение LightGBM по каждому включённому ТФ; sanity-базейны («предыдущий знак», логистическая регрессия); опционально CatBoost; отчёт walk-forward-метрик (AUC/log-loss по фолдам + агрегат) с заранее зафиксированными порогами приёмки (configs/validation).
- **Файлы**: `src/tradebot/ml/{train,registry,baselines}.py`, `src/tradebot/cli/train.py`, `reports/model_v1_*.md`, `tests/ml/test_registry.py` (загрузка модели проверяет манифест признаков).
- **Риски**: переобучение при малом числе баров; нестабильность метрик между фолдами. Митигация: пороги приёмки зафиксированы ДО обучения (D6); при непрохождении — этап НЕ принимается, идёт разбор (признаки/горизонт/полоса), а не «докрутка до зелёного».
- **Приёмка**:
  1. обучение детерминировано (seed): повторный прогон даёт идентичные метрики;
  2. реестр: модель загружается только с совпадающим манифестом признаков (тест на mismatch);
  3. отчёт содержит: метрики по фолдам, сравнение с обоими sanity-базейнами, вердикт по порогу;
  4. решение D4/P1 (LightGBM vs CatBoost) зафиксировано в decisions.md по фактическим цифрам (либо зафиксировано «порог не пройден» и план итерации).
  - Примечание: «приёмка этапа» ≠ «модель прибыльна». Пороги — диагностические.

## Этап B1. Симулятор и бэктест-отчёт

- **Цель**: `backtest/`: событийный симулятор (сигнал на закрытии t → fill на open t+1), модель издержек (commission_bps, slippage_bps из конфига, пометка «оценочные» — Q9), `SimulatedBroker` (позиция, кэш, запреты шорта сверх конфига), метрики (число сделок, hit-rate, PF, maxDD, PnL-кривая) и отчёт.
- **Файлы**: `src/tradebot/backtest/{simulator,costs,metrics,report}.py`, `src/tradebot/strategy/{signal_policy,position_manager}.py`, `src/tradebot/cli/backtest.py`, `tests/backtest/` (детерминированный golden-прогон; проверка, что fill никогда не бывает по цене бара t), `reports/backtest_v1_*.md`.
- **Риски**: оптимистичные филлы (lookahead в цене исполнения); издержки занижены. Митигация: тест «fill ≥ open t+1 по времени»; чувствительность PnL к commission/slippage — обязательный раздел отчёта.
- **Приёмка**:
  1. golden-тест воспроизводит эталонный отчёт бит-в-бит;
  2. на синтетике с известной «пилой» симулятор даёт ожидаемые PnL/издержки (ручной расчёт в тесте);
  3. отчёт по реальной модели (этап M2) сформирован: кривая PnL после издержек, таблица чувствительности к slippage ×2, вердикт без обещаний доходности;
  4. TEST-режим полностью автономен (без сети/токенов) — проверяется в CI.

## Этап L1. LIVE-фундамент: auth, инструменты, лимиты (read-only)

- **Цель**: `finam/`-адаптер поверх `finam-sdk==2.23.0`: AuthSession (авто-JWT, expires_at), TokenDetails → account_ids/readonly/md_permissions (лог без токенов); InstrumentsSource: GetAsset (min_step/decimals/lot_size), GetAssetParams (trade_lot_size/is_tradable), Schedule, Clock, Exchanges; кэш каталога; QuotaMonitor (GetUsageMetrics); клиентский rate-limiter ≤200 зап/мин/метод; маппинг ошибок FinamError → доменные; контрактные тесты на фейках + `for_testing()`-канал.
- **Файлы**: `src/tradebot/finam/{auth,instruments,errors,ratelimit}.py`, `src/tradebot/marketdata/interfaces.py`, `src/tradebot/cli/smoke_readonly.py`, `tests/finam/` (фейк-сервер/моки SDK), `reports/live_preflight_*.md`.
- **Риски**: pin SDK устаревает (changelog v2.x меняется квартально — S6); права токена без market data. Митигация: pre-flight печатает md_permissions и readonly; обновление SDK — отдельная задача с чтением changelog.
- **Приёмка** (на демо-токене, read-only):
  1. smoke-скрипт: аутентификация, список счетов, параметры SBER@MISX (lot_size, trade_lot_size, min_step, decimals), расписание ближайшей сессии, usage — всё в отчёте;
  2. ни одна торговая операция не выполнена (в логах нет PlaceOrder);
  3. секрет не появился ни в логах, ни в отчётах (grep-проверка в CI-джобе на примере утечки);
  4. контрактные тесты покрывают: 401→переавторизация, 429→pause, trade_lot_size=0→stop (S3j Рецепт 4).

## Этап L2. LIVE-данные: warmup, потоки, BarFinalizer, reconciliation данных

- **Цель**: FinamHistorySource (оконная загрузка Bars с учётом глубины: M1≤7д, M5/M15/H1≤30д — S5; кэш закрытых свечей; Q8 — размер окна подбирается эмпирически); FinamStreamSource (WS или gRPC SubscribeBars M5/других + SubscribeQuote); BarFinalizer (pending-паттерн, дедупликация, финализация по следующему timestamp — S3j Рецепт 6); Resampler(10m) поверх потока; reconnect-процедура (backoff 1→2→4→8→16→30+jitter → handshake → переподписки → REST-снимок → сверка пропущенных баров) ; D2-сверка: окно, загруженное из API, против CSV/ресэмплинга (расхождения → отчёт).
- **Файлы**: `src/tradebot/marketdata/{finam_history,finam_stream,bar_finalizer,reconnect}.py`, `src/tradebot/cli/stream_monitor.py` (наблюдатель: печатает финализированные бары, НИКАКИХ заявок), `tests/marketdata/` (фейк-поток: дубли, разрыв, out-of-order, snapshot-флаг), `reports/live_data_check_*.md`.
- **Риски**: поведение потока на клиринге/аукционах неизвестно (Q5); семантика timestamp API-баров (Q3) — определяется эмпирически на демо (сверка с расписанием). Митигация: монитор-лог нескольких сессий до включения сигналов; все выводы — в отчёт.
- **Приёмка**:
  1. stream_monitor ≥1 полная торговая сессия на демо: финализированные бары 5m/10m идут непрерывно, дубли не создают лишних баров (тест + лог);
  2. искусственный обрыв (kill соединения в тесте/вручную) → восстановление ≤60 с, пропущенные бары догружены REST-ом, разрывов в локальном хранилище нет;
  3. сверка API-баров против CSV на 30-дневном окне M5: расхождение цен ≤ установленного допуска, отчёт сохранён; семантика timestamp задокументирована фактами (обновление research.md Q3);
  4. сигнальные расчёты в LIVE-контуре используют те же FeatureBuilder/модель, что в TEST (проверяется трассировкой/тестом эквивалентности на общем окне).

## Этап L3. LIVE-исполнение на демо: dry-run → защищённые заявки

- **Цель**: ExecutionGateway: OrderRequest-валидация (шаг цены = min_step/10^decimals; штуки = лоты × trade_lot_size; client_order_id ≤20, детерминированный из сигнала; side/type/TIF по enum — S8f), DryRunBroker (полный журнал намерений без отправки), FinamBroker (PlaceOrder/CancelOrder/GetOrders/GetOrder, потоки ORDERS/TRADES, состояние UNKNOWN_RESULT при потере ответа — сверка, never blind retry), RiskGuards (allowlist демо-счёта, «ровно один счёт у токена» — S8i, лимиты количества/позиции/частоты, расписание, kill switch), PositionManager с reconciliation (GetAccount/GetOrders vs локальный журнал при старте/после обрывов/периодически).
- **Файлы**: `src/tradebot/execution/{interfaces,dry_run,finam_broker,risk_guards,kill_switch,reconcile}.py`, `src/tradebot/live/orchestrator.py`, `src/tradebot/cli/live.py` (флаги: --dry-run по умолчанию, --allow-orders — явный), `tests/execution/` (фейк-брокер: частичные филлы, реджекты, потеря ответа, дубли событий), `reports/live_demo_trial_*.md`.
- **Риски**: неизвестная модель исполнения демо (Q1) — результаты демо НЕ переносятся на бой; случайная отправка на реальный счёт. Митигация: allowlist account_id + валидация при старте + dry_run=true по умолчанию (паттерн FINAM_ENABLE_ORDERS, S3i); любое включение заявок — только после чек-листа Рецепта 7 (S3j).
- **Приёмка** (демо-счёт, полный доступ):
  1. сессия dry-run: сигналы и намерения журнал-ируются, ноль заявок отправлено (подтверждается GetOrders=пусто);
  2. после явного флага: одна лимитная заявка далеко от рынка (паттерн курса S3g) выставлена → статус ORDER_STATUS_NEW получен из потока ORDERS → отменена → статус CANCELED подтверждён сверкой; клиентский журнал совпал с брокерским (reconciliation=0 расхождений);
  3. тест «потерянный ответ»: имитация (фейк) переводит контур в UNKNOWN_RESULT, новые заявки блокируются до сверки;
  4. kill switch: создание файла немедленно прекращает выставление заявок (проверено в живой сессии);
  5. решение о боевых/реальных ордерах НЕ принимается — статус фиксируется в decisions.md (P7).

> Статус (фаза 5, интеграция): часть инструментов L1/L3 поставлена ДОСРОЧНО и
> в урезанном виде: `cli/run.py` (`python -m tradebot test | live-preflight`) —
> единая точка запуска; `live/gate.py` — многофакторный гейт (отказ до сети);
> `finam/broker.py` — ордерный адаптер (PlaceOrder/GetOrders/GetOrder/
> CancelOrder/GetAccount, UNKNOWN_RESULT-протокол, защита от дублей, сверка
> позиций) — реализован и проверен на подменном транспорте, НО не проверен в
> брокерской среде и заблокирован гейтом. Приёмка L1.1–L1.4 на демо-токене и
> ВСЯ приёмка L2/L3 (потоки, BarFinalizer, reconnect, оркестратор, живые
> сверки) — НЕ выполнены; до их выполнения LIVE-торговля запрещена
> (docs/live.md §5–§6).

## Этап L4 (опциональный, после L3). Наблюдаемость и длительный прогон

- **Цель**: структурированные логи по составу S3j Рецепт 8, метрики здоровья (латентность бара, частота reconnect, квоты GetUsageMetrics, расхождения сверки), алерты, длительный paper-прогон (≥2 недели сессий) с ежедневным отчётом; эксперимент со стаканом (Q4) — только здесь.
- **Файлы**: `src/tradebot/observability/*`, `src/tradebot/live/health.py`, дашборд-отчёты `reports/daily_*.md`.
- **Риски**: «молчащий поток» неотличим от спокойного рынка (S4) — health-метрики обязаны различать (heartbeat подписок, ERROR/EVENT-конверты).
- **Приёмка**: paper-прогон без ручных вмешательств пережил ≥3 обрыва связи с автовосстановлением; ежедневные отчёты полны; инцидентов «заявка без журнала» — ноль.

## Сквозные правила всех этапов

1. Никакого кода вне этапа; этап начинается только после приёмки предыдущего (исключение: параллельно D2 и F1).
2. Каждый этап добавляет тесты; CI зелёный — обязательное условие приёмки.
3. Все внешние факты, полученные на этапах L1–L3 (Q1, Q3-API, Q4, Q5, Q8), немедленно вносятся в research.md с датами — документация живая.
4. Секреты: только env; проверка на утечку в CI.
5. Ни один этап не обещает доходность; торговые метрики — диагностические; система не объявляется production-ready.

## Зависимости этапов

```
0 → D1 → D2 → F1 → F2 → M1 → M2 → B1 ─┐
                                        ├→ L3 → L4
        L1 (после 0, параллельно M/B) → L2 ─┘
```
