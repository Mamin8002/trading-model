## 1. Состав

| Модуль | Назначение |
|---|---|
| `execution/interfaces.py` | контракты: Signal, OrderIntent, Fill, RiskDecision/RiskRejection (коды отказов), PortfolioState, RiskContext |
| `execution/sizing.py` | расчёт размера позиции (фиксированный / по риску на сделку) |
| `execution/risk.py` | `RiskGuards` — лимиты, остановки, сверка позиции |
| `execution/simulator.py` | `SimulatedBroker` — правила исполнения (next-open, слиппедж, комиссии, стоп/цель, конфликт) |
| `execution/journal.py` | JSONL-журнал решений/сделок + аудит-строки + маскирование |
| `backtest/engine.py` | `EventSimulator` — событийный цикл по барам |
| `backtest/results.py` | результаты (net после издержек, maxDD, turnover, сделки) + markdown-отчёт с допущениями |
| `strategy/signals.py` | источники сигналов: `ModelSignalSource` (артефакт фазы 3), `ScriptedSignalSource` (детерминированные сценарии) |
| `cli/simulate.py` | `python -m tradebot.cli.simulate` (офлайн: CSV + артефакт модели) |

Конфигурация: секции `risk`, `instrument`, `simulation` (схема в
`config/schema.py`, пример — `configs/sim_demo.yaml`, **все значения в демо-конфиге
помечены как ДЕМО-допущения**).

## 2. Модель исполнения (fill model)

- Решение принимается **после закрытия** сигнального бара t (сигналы строятся по
  финальным барам; незакрытые свечи не используются — D9).
- Исполнение — **не раньше следующей доступной цены**: по `open` бара t+1
  с проскальзыванием `slippage_bps` **невыгодной стороной** (buy: `open·(1+slip)`,
  sell: `open·(1−slip)`), результат ограничивается диапазоном бара `[low, high]` —
  цены за пределами бара не выдумываются.
- `close` сигнальной свечи сохраняется в журнале как `reference_price` с пометкой
  «справочно, НЕ цена исполнения» и в расчёте филла не участвует.
- Если следующего бара нет (конец данных) — намерение не исполняется, в журнал
  пишется отказ `no_next_bar`.
- Комиссия: `max(commission_bps·notional/10⁴, commission_min_quote)` — только из
  явного конфига; при неза заданных `commission_bps`/`slippage_bps` симулятор
  **не запускается** (SimConfigError со списком недостающих полей).
- Позиция на конец данных **не закрывается фиктивной сделкой**: warning
  `position_open_at_end`, оценка mark-to-market по последнему close.
- Long-only, один символ, одна позиция; реверсы не поддержаны (встречной BUY при
  открытой позиции игнорируется с предупреждением).

## 3. Риск-контроль

### 3.1 Явность параметров (требование ТЗ)

Скрытые финансовые значения отсутствуют: у «пустой» `RiskConfig` все лимиты
`None`. Симулятор стартует только если явно заданы: `initial_capital_quote`,
режим размера (`position_units` ИЛИ `risk_per_trade_quote` ИЛИ
`risk_per_trade_pct` — ровно один), `max_position_units`, `max_orders_per_day`,
`daily_loss_limit_quote`, `max_drawdown_pct`, `max_data_age_seconds`, а также
`simulation.commission_bps` и `simulation.slippage_bps`. Недостающее перечисляется
в ошибке; каждый непройденный гейт пишет в журнал отказ с кодом, именем лимита,
лимитным и наблюдаемым значением.

### 3.2 Размер позиции

- фиксированный режим: `position_units` используется как есть; некратность
  `lot_size_units` — отказ `invalid_lot_multiple` (пользовательское значение
  молча не округляется);
- рисковый режим: `units = floor(risk_amount / |entry − stop|)`, округление вниз
  до лота; `risk_amount` — `risk_per_trade_quote` или % от текущего капитала;
  **стоп обязателен** (иначе отказ `sizing_stop_required` — расстояние до стопа
  не подбирается); в этом режиме размер дополнительно ограничивается капиталом
  (стоимость + комиссия) и `max_position_units` с фиксацией `capped_by` в журнале;
- цена входа для сайзинга на момент решения — оценка `close_t·(1+slip)` (open
  следующего бара ещё неизвестен; допущение печатается в отчёте); фактический
  филл может отличаться — риск-лимиты проверяются повторно по `reference_price`.

### 3.3 Лимиты и остановки

| Гейт | Код отказа | Остановка? |
|---|---|---|
| kill switch / любой активный halt | `strategy_halted` | — |
| ошибка источника данных | `invalid_data` | да (`data_source_error`) |
| невалидный бар (OHLC/порядок) | `invalid_data` | да, цикл прерывается |
| устаревшие данные (возраст > `max_data_age_seconds`) | `stale_data` | да |
| просадка от пика > `max_drawdown_pct` | `drawdown_limit` | да (при `halt_on_limit_breach`) |
| дневной убыток ≥ `daily_loss_limit_quote` | `daily_loss_limit` | да (при `halt_on_limit_breach`) |
| заявки в день ≥ `max_orders_per_day` | `order_count_limit` | нет (только отказ) |
| позиция+заявка > `max_position_units` | `max_position_exceeded` | нет |
| notional+комиссия > cash | `insufficient_capital` | нет |
| продажа без позиции / сверх позиции | `no_position_to_close` / `short_not_allowed` | нет |
| стоп/цель не кратны `price_step` (если подтверждён) | `invalid_price_step` | нет |
| стоп ≥ входа или цель ≤ входа (long) | `invalid_stop_target` | нет |
| рассинхрон позиции (журнал филлов ≠ портфель) | `position_inconsistency` | да, цикл прерывается |

**Порядок действия остановки (консервативный, документированный):** halt
блокирует НОВЫЕ ВХОДЫ; защитные выходы (стопы, сигналы выхода) продолжают
исполняться; автоматическое закрытие позиции не выполняется (fabrication
сделок запрещена). Дневные счётчики (`day_orders`, `day_realized_pnl`)
сбрасываются на границе локального дня (`data.source_timezone`).

Сверка позиции: `RiskGuards` ведёт независимый накопительный учёт единиц по
филлам; после каждого исполнения он сравнивается с портфелем — расхождение
(внешняя порча, баг учёта) немедленно останавливает симуляцию.

### 3.4 Параметры инструмента

`instrument.price_step` и `instrument.lot_size_units` должны происходить из
подтверждённого источника: спецификация торговой пары вашей криптобиржи
(например tickSize/stepSize в exchangeInfo). `None` = параметр не подтверждён:
зависимые проверки безопасно откладываются с предупреждением в журнал/отчёт
(значения не подставляются). Количество — целые единицы базового актива;
дробные количества (stepSize биржи) отложены до реализации ордерного шлюза
(decisions D14).

## 4. Стопы, цели и конфликт в одном баре

Стоп/цель задаются либо явно в сигнале, либо через `simulation.signal.stop_bps` /
`target_bps` от **цены фактического входа** (округление до `price_step`
консервативное: стоп длинной позиции — ВВЕРХ по сетке, сработает не позже
заданного; цель — ВНИЗ). Проверка — по `low/high` каждого следующего бара,
включая бар входа.

**Конфликт:** если в одном баре `low ≤ stop` И `high ≥ target`, порядок касаний
внутри бара неизвестен. Автоматический выбор выгодного сценария запрещён.
Две документированные политики (`simulation.conflict_policy`):

1. `stop_first` (по умолчанию) — консервативное правило: исполняется СТОП
   (худший для длинной позиции исход). Событие помечается в журнале
   (`stop_target_conflict`), fill получает cause `stop_target_conflict`;
2. `require_intrabar_data` — симуляция останавливается
   (`intrabar_data_required`) с требованием предоставить внутрибарные данные
   (тики/L2); выход НЕ фабрикуется, позиция остаётся как есть.

Гэп через стоп: если `open ≤ stop`, исполнение по `open` (хуже стопа,
cause `gap_through_stop`) — реалистично и консервативно. Гэп выше цели:
исполнение по `open` (реалистичная механика лимитного выхода; единственное
«улучшение» цены, соответствующее биржевой логике, а не выбору сценария).
Проскальзывание применяется к каждой цене исполнения (включая стопы/цели) —
заведомо пессимистичное допущение.

## 5. Журнал решений и сделок (аудит)

Формат: JSON Lines, по одному событию в строке. Виды: `signal`, `risk_decision`,
`intent`, `fill`, `halt`, `warning`, `state`. Общие поля каждой записи:
`schema_version`, `written_at` (UTC), `kind`, `symbol`, `timeframe`,
`model_version` (для модельного источника — `experiment_id:fingerprint`
артефакта фазы 3).

Восстановимость решения (критерий приёмки):
- `signal`: proba, пороги, стоп/цель, метка бара решения;
- `risk_decision`: approved, список rejections (код, сообщение, лимит, лимитное и
  наблюдаемое значение), выполненные проверки;
- `intent`: количество, `reference_price` с пометкой «НЕ цена исполнения»,
  режим сайзинга, `planned_execution`;
- `fill`: план vs факт (`raw_price` → `price`), `slippage_bps`,
  `commission_quote`, `cause`, cash/units после;
- `halt`/`warning`: причина и детали (включая конфликт стоп/цель и
  `position_open_at_end`).

Секреты: все строки журнала проходят через `SecretMasker` (`config/env.py`,
маска вида `***SECRET***`); ключи и счета в поля не кладутся структурно. Значения короче 4 символов маскировщиком не
регистрируются (защита от порчи текста).

Чтение: `tradebot.execution.journal.read_journal(path)`, человекочитаемый
аудит — `audit_line(record)` / `iter_audit(path)`.

## 6. Результаты и отчёт

`compute_results` + `render_simulation_report`: капитал → итоговый equity,
net_return (после комиссий и слиппеджа), суммарные комиссии, оценка издержек
слиппеджа (Σ|price−raw|·units), turnover, число входов/завершённых сделок,
hit-rate, profit factor, maxDD по кривой капитала, exposure, годовые CAGR/Sharpe
(источник `bars_per_year` фиксируется), отказы по кодам, halt-события, conflicts,
таблица сделок, предупреждения. Обязательные разделы отчёта: допущения
(комиссии/слиппедж/исполнение/годовой пересчёт), рисковые лимиты (включая
«НЕ ЗАДАН»), ограничения симулятора, дисклеймер.

## 7. Ограничения симулятора (явно НЕ моделируется)

- частичные исполнения, ликвидность стакана, очередь заявок — весь объём
  исполняется по расчётной цене бара;
- внутрибарная траектория: только правила стоп/цель/конфликт из §4;
- шорты, маржа/плечо, налоги;
- мультисимвольный портфель и аллокация;
- фактические тарифы биржи: комиссии/слиппедж — пользовательские допущения;
- LIVE-события (реальные филлы, reconciliation с биржей) — не реализованы
  (docs/live.md, roadmap E3);
- маржа/плечо/funding/ликвидации и шорты — не моделируются (decisions D15).

## 8. Запуск

```powershell
# установка (один раз)
python -m pip install -e ".[dev,ml]"

# ручная проверка фазы 4 (офлайн, детерминированная) — ожидает RESULT: PASS (16/16)
python scripts\manual_checks\check_phase_04_simulation.py

# симуляция на своих данных: CSV из data.csv_dir + артефакт модели фазы 3
python -m tradebot.cli.simulate --config configs\sim_demo.yaml --timeframe 5m --model-dir models\<артефакт>

# тесты
python -m pytest
```

Коды возврата `simulate`: 0 — выполнено (остановки/отказы отражены в отчёте и
журнале); 2 — ошибка/неполнота конфигурации; 4 — ошибка данных/модели/симуляции.
