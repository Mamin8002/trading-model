# Decisions: ключевые проектные решения и аргументы

Дата: 2026-10-21. Формат: решение → статус → контекст → аргументы → альтернативы → последствия.
Ссылки на факты — по нумерации источников в [research.md](research.md) (S1–S9), вопросы — Q1–Q9 там же.

---

## D1. Единый внутренний контракт данных вместо работы «напрямую с CSV/API»

- **Решение**: все источники (CSV, REST Bars, WS BARS) приводятся к внутреннему типу `Bar` (ts_open UTC, OHLCV, source, is_final) в модуле `data/`; семантика метки времени и таймзона задаются конфигом и проверяются валидатором.
- **Статус**: принято.
- **Контекст**: документация API не фиксирует, является ли `Bar.timestamp` началом или концом интервала (Q3); CSV WISEPLAT внутренне противоречив (скрипт сдвигает метку на конец бара, данные похожи на начало) (S9e/S9h); REST/WS/gRPC по-разному кодируют decimal (S3f).
- **Аргументы**: ошибка сдвига на один бар — это гарантированная утечка/опоздание сигнала; три протокола с тремя decimal-представлениями требуют одной точки нормализации; валидатор ловит битые файлы до обучения, а не в отчёте PnL.
- **Альтернативы**: (а) работать с «сырыми» фреймами из каждого источника — отклонено: расползание допущений по всем модулям; (б) принять семантику «на глаз» — отклонено: недопустимый риск.
- **Последствия**: обязателен этап D1 (валидатор + детектор семантики метки) до любых ML-этапов.

## D2. История для обучения — из CSV; Finam API — не источник длинной истории

- **Решение**: обучение и бэктест используют пользовательские CSV (MOEX). API `Bars` применяется только для LIVE-warmup и контрольных сверок.
- **Статус**: принято.
- **Контекст**: подтверждённая глубина истории API: M1 — 7 дней, M5/M15/H1 — 30 дней (S5, S3e). Для обучения модели на годах данных этого недостаточно. WISEPLAT по той же причине брал историю с MOEX через aiomoex (S9a/S9e).
- **Аргументы**: требование длинной истории для walk-forward; CSV уже есть у заказчика в фиксированном формате; независимость TEST-контура от сети и токенов.
- **Альтернативы**: (а) копить историю через API инкрементально — годится только как дополнение (периодический snapshot-джоб может расширить локальный архив, но годы назад не вернёт); (б) платные сторонние источники — вне текущего скоупа.
- **Последствия**: нужен этап D2 — сверка распределений CSV vs API на перекрывающемся окне (30 дней M5): расхождения цен/объёмов/границ сессий должны быть объяснены до прогона LIVE-warmup из API.

## D3. Таймфрейм 10m строится локальным ресэмплингом 5m→10m (единый модуль для TEST и LIVE)

- **Решение**: 10m не запрашивается у API; строится `Resampler`-ом из 5m (в LIVE — из потока M5; в TEST — из CSV 5m или используется готовый CSV 10m после сверки с ресэмплингом).
- **Статус**: принято (вынужденное — ограничение API).
- **Контекст**: enum `TimeFrame` не содержит M10 ни в REST, ни в gRPC, ни в WS BARS (S8f marketdata_service.proto, S5) — **[РАСХОЖДЕНИЕ]** с ТЗ, где 10m заявлен поддерживаемым таймфреймом.
- **Аргументы**: 10m = детерминированная агрегация 2×5m (open/high/low/close/volume правила однозначны); один код в обоих режимах устраняет TEST/LIVE-рассинхрон; M5-поток даёт 10m-бар с задержкой не более одного 5m-бара.
- **Альтернативы**: (а) ресэмплинг из 1m — точнее на границах, но M1-поток/история ограничены 7 днями и тяжелее по трафику; оставлено как опция конфига `base_timeframe: 1m`; (б) убрать 10m из ТЗ — продуктовое решение, вынесено заказчику; (в) брать M10 с MOEX ISS напрямую (как WISEPLAT) — дополнительный внешний зависимый канал с 15-минутной задержкой, отклонено для LIVE.
- **Последствия**: LIVE-сигналы на 10m финализируются на закрытии чётного 5m-бара; это зафиксировано в контрактной схеме (`base_timeframe`) и тестах эквивалентности.

## D4. Модель: градиентный бустинг (LightGBM основной, CatBoost контрольный); нейросети отложены

- **Решение**: табличные признаки + LightGBM; CatBoost как второй кандидат в сравнении; Transformer/LSTM — только при выполнении явных условий (см. architecture.md §5.1).
- **Статус**: принято как стартовое; пересматривается по итогам этапа M2.
- **Контекст**: ТЗ предписывает табличные признаки и называет LightGBM/CatBoost основными кандидатами; референс WISEPLAT (CNN по картинкам) автор сам признаёт неприбыльным (S9a) и ТЗ прямо исключает картинки.
- **Аргументы**: сотни–тысячи строк признаков на символ — типичная зона превосходства бустинга над глубокими моделями; скорость итераций и интерпретируемость (importance/SHAP) критичны на этапе отладки утечек; меньше инфраструктурного риска. CatBoost проверяет гипотезу «ordered boosting меньше переобучается на рядах».
- **Альтернативы**: LSTM/Transformer сразу — отклонено: нет подтверждённого преимущества при наших объёмах данных, дороже в отладке, требования ТЗ; линейные модели — останутся как sanity-базейн (обязательный порог: бустинг должен обыгрывать «предсказание предыдущего знака» и логистическую регрессию на том же сплите).
- **Последствия**: модельный реестр хранит артефакт + манифест (конфиг, набор признаков, сплиты, метрики); промоушен в LIVE — отдельный явный шаг.

## D5. Целевая переменная: forward-return через H баров с нейтральной полосой (классификация), H настраивается per-timeframe

- **Решение**: `y` из `close[t+H]/close[t] − 1` с нейтральной полосой ≈ издержки; `horizon_bars` и `lookback_bars` — параметры каждого таймфрейма в конфиге (требование ТЗ).
- **Статус**: принято как v1; ablation на этапе M1.
- **Контекст**: двух-таймфреймовая схема WISEPLAT (вход на M1, метка на M10) — частный случай нашей схемы (H баров младшего ТФ ≈ 1 бар старшего) (S9c/S9f); при этом их метка «close выше предыдущего» игнорирует издержки — критикуем.
- **Аргументы**: нейтральная полоса сразу кодирует экономику сделки (классы «движение меньше издержек» не должны торговаться); фиксированный горизонт проще для walk-forward и симулятора; пер-ТФ настройка удовлетворяет ТЗ без усложнения контракта.
- **Альтернативы**: (а) тройной барьер (TP/SL/time) — методологически сильнее для стратегии со стопами, но требует стоп-логики в симуляторе; отложено до v2 (после работы базового контура); (б) регрессия forward-return — оставляем в ablation; (в) метка «направление к открытию следующего бара» — слишком короткий горизонт относительно издержек на 1m.
- **Последствия**: embargo в сплитах обязателен (≥ H баров); симулятор исполняет на open t+1.

## D6. Валидация: purged walk-forward с embargo; фиксированные пороги приёмки до обучения

- **Решение**: только временные сплиты (walk-forward), удаление «пурж»-зоны и embargo ≥ horizon; пороги метрик записываются в конфиг валидации заранее; audit-отчёт «random-split vs walk-forward» обязателен.
- **Статус**: принято.
- **Аргументы**: стандарт защиты от leakage на перекрывающихся метках; большая дельта между наивным и честным сплитом — индикатор утечки (architecture.md §6.8).
- **Альтернативы**: случайный KFold — отклонён (утечки будущего); anchored single split — слабее по устойчивости оценок.
- **Последствия**: стоимость обучения растёт (несколько фолдов), но это плата за доверие к цифрам.

## D7. Транспорт LIVE: официальный Python SDK `finam-sdk` (gRPC) за собственным интерфейсом

- **Решение**: интеграция через `finam-sdk==2.23.0` (pin), обёрнутый в адаптеры `finam/` за интерфейсами `marketdata/execution` (research.md §2.9, S8b/S8d).
- **Статус**: принято; pin пересматривается только с чтением changelog (S3k).
- **Аргументы**: SDK берёт на себя JWT-жизненный цикл (SubscribeJwtRenewal), retry UNAVAILABLE/429-pushback, типизированные ошибки; официальный пример стратегии построен на SDK и прямо не рекомендует самописный транспорт (S8i); gRPC-контракты типизированы proto-файлами. Важный нюанс PyPI: пакет называется `finam-sdk`, импорт `finam_trade_api`; пакет `finam-trade-api` в PyPI — **сторонний** (S3k, S8d).
- **Альтернативы**: (а) чистый REST/WS руками — больше кода и ошибок в токенах/ретраях; остаётся запасным транспортом за тем же интерфейсом (WS-конверты документированы AsyncAPI); (б) неофициальные клиенты (FinamPy/FinamTradeApiPy как у WISEPLAT) — отклонено: нацелены на устаревший API (S8e, S9i).
- **Последствия**: стримы SDK не ретраит — переподключение/reconciliation — наша зона ответственности (S8b); Python ≥3.10 становится требованием окружения.

## D8. Тестовая среда: демо-счёт + dry-run по умолчанию; неизвестные правила демо изолированы BrokerGateway

- **Решение**: LIVE-проверки — только на демо-счёте (создаётся в разделе Токенов портала, S3b); по умолчанию `dry_run: true` и `allow_orders: false`; включение заявок — отдельный явный шаг приёмки этапа L3; модель исполнения демо неизвестна (Q1) и не должна влиять на код (интерфейс).
- **Статус**: принято.
- **Аргументы**: официальные примеры курса сами используют демо + явный флаг разрешения (S3g/S3i, паттерн FINAM_ENABLE_ORDERS);_recipe 7 (S3j) задаёт минимальный набор предохранителей — берём его как обязательный чек-лист RiskGuards.
- **Альтернативы**: песочница-эмулятор API полностью локальный — частично делаем (SimulatedBroker в TEST), но он не заменяет демо-проверку транспорта/авторизации.
- **Последствия**: до закрытия Q1 результаты на демо не экстраполируются на боевое исполнение; решение о реальных ордерах на этом этапе не принимается (ограничение ТЗ).

## D9. Свечи: решения только по завершённым барам; pending-бар — явное состояние

- **Решение**: `BarFinalizer` хранит последнюю свечу как pending, обновляет при том же timestamp, финализирует только при появлении более позднего; стратегия вызывается один раз на финализированный бар; дубли дедуплицируются.
- **Статус**: принято.
- **Контекст**: официальный Рецепт 6 (S3j) и FAQ (S4 pogranichnye-sluchai) предписывают именно это; WISEPLAT независимо делал то же (отбрасывал последнюю свечу при поллинге) (S9g).
- **Аргументы**: pending-бар мутирует (high/low/close/volume) — сигнал по нему неминуемо «заглядывает в будущее» внутри бара; один сигнал на бар устраняет дребезг.
- **Последствия**: латентность сигнала = закрытие бара (+ финализация соседнего); для 10m — плюс один 5m-бар (D3).

## D10. Конфигурация: декларативный YAML + pydantic-схема + хэш конфига в артефактах

- **Решение**: вся настройка (ТФ, lookback, horizon, метка, модель, валидация, издержки, LIVE-предохранители) — в YAML со строгой схемой; секреты — только env; каждый артефакт (датасет/модель/отчёт) несёт хэш конфига.
- **Статус**: принято.
- **Контекст**: ТЗ требует per-timeframe lookback/horizon; WISEPLAT держал конфиг Python-классами и токены в Config.py (S9c/S9d) — критикуем: секрет в файле рядом с кодом, отсутствие валидации.
- **Аргументы**: воспроизводимость экспериментов; валидация опечаток до запуска; аудиторский след; требование безопасности S3b/S4 (секреты вне git/логов).
- **Последствия**: CLI принимает путь к конфигу; «прод-настройки» LIVE (account_id, лимиты) валидируются особенно строго (например, отказ торговать, если токену видно ≠ 1 счёт — паттерн S8i).

## D11. Ошибки и повторы: официальная таблица безопасных повторов как норма; «неизвестный результат» — отдельное состояние

- **Решение**: retry-матрица из research.md §2.8 встроена в `finam/`-адаптер и RiskGuards; PlaceOrder без ответа переводит контур в состояние UNKNOWN_RESULT: стоп новых заявок → сверка GetOrders/ORDERS → решение оператора/автоматическая отмена по client_order_id.
- **Статус**: принято.
- **Аргументы**: прямое требование документации (S3l, S4 chego-ne-delat: «две заявки вместо одной, обе настоящие»); client_order_id ≤ 20 символов, детерминированный из сигнала (паттерн S8i), делает сверку возможной.
- **Последствия**: журнал команд/ответов/событий обязателен (S3j Рецепт 8); без него приёмка LIVE-этапов не проходит.

## D12. Стакан и L2-признаки: опционально, после эмпирики на демо

- **Решение**: ORDER_BOOK/INSTRUMENT_TRADES не входят в v1-контур признаков; интерфейс `StreamSource` их поддерживает; включение — только после проверки Q4 (глубина/частота) и доказанной полезности.
- **Статус**: принято.
- **Аргументы**: глубина стакана документацией не гарантируется (Q4); свечные признаки закрывают требования ТЗ; меньшая поверхность надёжности на старте.
- **Последствия**: маркетинговое «L2» (S1) остаётся непроверенной возможностью до этапа-эксперимента.

## D13. Референс WISEPLAT: объект анализа, не источник кода и не подтверждение подхода

- **Решение**: заимствуются только: формат CSV-контракта (совпал с ТЗ), идея двух ТФ «признаки/метка» (обобщена до per-TF horizon), паттерн отсечения незакрытой свечи. Код не копируется; CNN-подход не переносится; интеграция с API переписывается под новый API.
- **Статус**: принято.
- **Контекст**: проект не обновлялся с 21.11.2023, написан под старый API (comon-токены, security_board), торговля на задержанных на 15 минут данных MOEX, рыночные ордера с плечом без стопов и проверки денег, состояние позиции только в памяти (S9a/S9c/S9d/S9g); автор прямо указывает неприбыльность стратегии.
- **Аргументы**: несовместимость с текущим API подтверждена MIGRATION_GUIDE (S8e); отсутствие guardrails противоречит официальным рецептам (S3i/S3j); прибыльность не заявлена даже автором.
- **Последствия**: в roadmap нет задач «портировать WISEPLAT»; есть задача «сверить наши CSV с его форматом» (D1/D2).

## D14. Границы TEST/LIVE: инвариантность ядра, различие только в шлюзах

- **Решение**: features/labels/strategy/model — общие; режим определяется подстановкой `HistorySource/StreamSource` и `BrokerGateway` фабрикой из конфига; LIVE добавляет обязательные слои (RiskGuards, reconciliation, BarFinalizer на потоке).
- **Статус**: принято.
- **Аргументы**: устраняет класс ошибок «в бэктесте одна логика, в LIVE другая»; тесты ядра не требуют сети; dry-run/демо/real — уровни одного интерфейса исполнения.
- **Последствия**: контрактные тесты шлюзов (фейки) обязательны; расхождение CSV-истории и API-данных (D2) — единственный допустимый источник TEST/LIVE-разницы в данных, и он измеряется.

## D15. Статус системы

- **Решение**: система проектируется как исследовательский контур (TEST) + защищённый LIVE-контур на демо с dry-run по умолчанию. Она **не** объявляется production-ready; доходность **не** обещается; все торгово-финансовые результаты — диагностические.
- **Статус**: принято (соответствует ограничениям ТЗ).
