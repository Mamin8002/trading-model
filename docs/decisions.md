# Decisions: ключевые проектные решения и аргументы

Дата редакции: 2026-10-21 (перевод проекта в крипторежим). Формат: решение → статус → аргументы → альтернативы → последствия.

> История: изначально проект строился вокруг брокерского API и биржевых акций.
> Эта интеграция ПОЛНОСТЬЮ УДАЛЕНА (код, конфиги, зависимости, документация);
> решения ниже описывают текущий криптовалютный каркас. Номерация сохранена
> там, где решение осталось в силе.

---

## D1. Единый внутренний контракт данных вместо работы «напрямую с CSV/API»

- **Решение**: все источники (сейчас — локальные CSV; в будущем — REST/WS биржи) приводятся к внутреннему типу `Bar` (ts_open UTC, OHLCV, source, is_final) в модуле `data/`; семантика метки времени и таймзона источника задаются конфигом ЯВНО и проверяются валидатором.
- **Статус**: принято.
- **Аргументы**: ошибка сдвига метки на один бар — это гарантированная утечка/опоздание сигнала; разные биржи по-разному кодируют время и объёмы — нужна одна точка нормализации; валидатор ловит битые файлы до обучения, а не в отчёте PnL.
- **Альтернативы**: (а) работать с «сырыми» фреймами из каждого источника — отклонено: расползание допущений; (б) принимать семантику метки «на глаз» — отклонено: недопустимый риск.
- **Последствия**: валидатор и явная `timestamp_semantics` обязательны до любых ML-этапов.

## D2. История — из локальных CSV; биржевой API к данным не подключён

- **Решение**: обучение, валидация и симуляция используют только пользовательские CSV. Сетевые источники рыночных данных в проекте ОТСУТСТВУЮТ; их появление возможно только через интерфейсы `marketdata/` при реализации биржевого адаптера (отдельная задача).
- **Статус**: принято.
- **Аргументы**: офлайн-контур воспроизводим, не требует ключей и сети; длинная история криптопар легко выгружается в CSV (экспорты бирж, например Binance Vision); TEST-результаты не зависят от доступности API.
- **Альтернативы**: (а) скачивание истории через API при запуске — отклонено до реализации адаптера (секреты, сеть, лимиты); (б) сторонние платные провайдеры — вне скоупа.
- **Последствия**: подготовка данных (выгрузка, проверка формата) — ответственность пользователя; проект предоставляет валидатор и CLI проверки.

## D3. Таймфрейм 10m строится локальным ресэмплингом из 5m/1m

- **Решение**: 10m не ожидается от источника; строится `Resampler`-ом из `base_timeframe` (5m по умолчанию, опция 1m). Правило обязательности `base_timeframe` для 10m закреплено в схеме конфига.
- **Статус**: принято.
- **Аргументы**: нативных 10-минутных свечей криптобиржи обычно не отдают (типовые наборы: 1m/3m/5m/15m/30m/1h/...); 10m = детерминированная агрегация 2×5m; один код ресэмплинга в TEST и (в будущем) LIVE устраняет рассинхрон.
- **Альтернативы**: (а) убрать 10m — отклонено: таймфрейм в требованиях проекта; (б) ресэмплинг из 1m — оставлен опцией конфига.
- **Последствия**: тест эквивалентности «1m→10m == 1m→5m→10m» обязателен; неполные интервалы никогда не выдаются за полные.

## D4. Модель: градиентный бустинг (LightGBM основной, CatBoost контрольный); нейросети отложены

- **Решение**: табличные признаки + LightGBM; CatBoost — второй кандидат в сравнении (не подключён, P1); Transformer/LSTM — только при выполнении явных условий (architecture.md §5.1).
- **Статус**: принято как стартовое.
- **Аргументы**: сотни–тысячи строк табличных признаков — типичная зона превосходства бустинга; скорость итераций и интерпретируемость критичны на этапе отладки утечек; лёгкие CPU-зависимости под Windows/Linux/macOS.
- **Альтернативы**: LSTM/Transformer сразу — отклонено; линейные модели — остаются sanity-базейном (бустинг обязан обыгрывать «предыдущий знак» и логрег на том же сплите).
- **Последствия**: реестр моделей хранит артефакт + манифест (конфиг, признаки, сплиты, метрики, seed).

## D5. Целевая переменная: forward-return через H баров с нейтральной полосой

- **Решение**: `y` из `close[t+H]/close[t] − 1` с нейтральной полосой ≈ издержки; `horizon_bars`/`lookback_bars` — явные параметры каждого таймфрейма.
- **Статус**: принято как v1; triple-barrier отложен (P2).
- **Аргументы**: нейтральная полоса кодирует экономику сделки (движение меньше издержек не должно торговаться); для крипторынка издержки = комиссия биржи + слиппедж, задаются пользователем явно.
- **Последствия**: embargo в сплитах обязателен (≥ H баров); симулятор исполняет на open следующего бара.

## D6. Валидация: purged walk-forward с embargo; пороги приёмки фиксируются ДО обучения

- **Решение**: только временные сплиты, purge-зона и embargo ≥ horizon; пороги метрик — в конфиге заранее; audit-отчёт «random-split vs walk-forward» обязателен.
- **Статус**: принято.
- **Аргументы**: стандарт защиты от leakage на перекрывающихся метках; большая дельта между наивным и честным сплитом — индикатор утечки.
- **Последствия**: «докрутка до зелёного» по валидации запрещена; непрохождение порогов — повод разбора, а не изменения порогов.

## D7. Любой внешний транспорт — за бирженезависимыми интерфейсами

- **Решение**: потребители (стратегия, симулятор, LIVE-контур) зависят только от портов `marketdata/interfaces.py` (HistorySource, QuoteSnapshotSource, OrderBookSnapshotSource, StreamSource) и `execution/interfaces.py` (BrokerGateway). Конкретная биржа подключается адаптером в `exchange/` (сейчас реализаций нет).
- **Статус**: принято.
- **Аргументы**: смена биржи/транспорта (REST/WS) не меняет ядро; TEST-контур не требует сети; контрактные тесты пишутся на фейках.
- **Последствия**: будущий адаптер обязан реализовать порты без их изменения; детали протоколов конкретной биржи не просачиваются в ядро.

## D8. LIVE заблокирован до реализации биржевого адаптера; многофакторный гейт

- **Решение**: ордерный контур недоступен: `exchange.base.EXCHANGE_INTEGRATION_AVAILABLE = False` — обязательное условие №0 многофакторного LIVE-гейта (`live/gate.py`). Даже при `run.mode: LIVE`, флаге `--allow-live`, env-подтверждении и `live.allow_orders: true` гейт отказывает. По умолчанию всё выключено; kill-switch-файл блокирует заявки дополнительно.
- **Статус**: принято.
- **Аргументы**: нельзя называть готовым то, что не реализовано и не проверено; явная блокировка честнее скрытых заглушек; многофакторность исключает случайное включение.
- **Альтернативы**: (а) убрать LIVE-код целиком — отклонено: гейт и контракты понадобятся адаптеру; (б) «dry-run через биржу» — невозможен без API-клиента.
- **Последствия**: включение LIVE — отдельный проект (roadmap E2/E3) с проверкой на тестнете/демо биржи.

## D9. Свечи: решения только по завершённым барам; pending-бар — явное состояние

- **Решение**: незакрытая свеча хранится как pending (`is_final=False`), стратегия вызывается только на финализированном баре; в будущем потоковом адаптере обязателен BarFinalizer (биржевые потоки мутируют текущую свечу).
- **Статус**: принято.
- **Аргументы**: сигнал по мутирующему бару «заглядывает в будущее» внутри бара; один сигнал на бар устраняет дребезг.
- **Последствия**: латентность сигнала = закрытие бара; ресэмплинг игнорирует non-final бары с явной пометкой.

## D10. Строгая декларативная конфигурация (pydantic, extra="forbid")

- **Решение**: YAML + строгая схема; опечатка/лишнее поле — ошибка загрузки. Финансовые параметры (капитал, комиссии, слиппедж, лимиты, шаги цены) — только явные значения, скрытые дефолты запрещены. Секреты в конфиге запрещены — только имена env-переменных.
- **Статус**: принято.
- **Последствия**: удалённые секции (например, прежняя брокерская) отклоняются схемой — старые конфиги не запускаются молча.

## D11. Время: единый стандарт UTC, рынок 24/7

- **Решение**: внутренний стандарт меток — UTC (timezone-aware, bar_open). Naive-метки CSV трактуются в `data.source_timezone` (по умолчанию UTC — стандарт криптоэкспортов); ISO-метки со смещением уважаются. Крипторынок круглосуточный: базовый календарь — 24/7 (`always_on_calendar`, окно 00:00–24:00 UTC); сессионные окна поддерживаются для бирж с техобслуживаниями. Суточные границы риск-лимитов — в `source_timezone` (по умолчанию UTC).
- **Статус**: принято.
- **Аргументы**: UTC устраняет двусмысленность летнего времени и локальных зон; биржевые экспорты криптопар отдают свечи в UTC; 24/7 — факт крипторынка (годовой пересчёт: `trading_days_per_year: 365`).
- **Последствия**: пользователь обязан подтвердить семантику метки (`timestamp_semantics`) для своей выгрузки; документация фиксирует правило в data.md §2–3.

## D12. Символ инструмента: тикер криптопары; формат ticker@mic удалён

- **Решение**: `data.symbols[].ticker` — строковый идентификатор пары в формате биржи (например `BTCUSDT` или `BTC/USDT`); `symbol` совпадает с тикером. Прежний составной формат `ticker@mic` удалён вместе с брокерской интеграцией.
- **Статус**: принято.
- **Аргументы**: MIC-коды — понятие традиционных бирж; криптопары идентифицируются тикером пары; сопоставление с внутренними символами конкретной биржи появится в её адаптере.
- **Последствия**: старые конфиги с полем `mic` отклоняются схемой (extra=forbid).

## D13. Дробный объём: `Bar.volume` — неотрицательный float

- **Решение**: объём бара — число с плавающей точкой (int тоже принимается). CSV-загрузчик принимает дробные значения без округления; отрицательные и нечисловые — ошибка `E_VOLUME_INVALID`. Единицы объёма объявляются в `data.volume_units` (`base_asset` | `quote_asset`).
- **Статус**: принято.
- **Аргументы**: объёмы криптопар в базовом активе дробные (например 0.12345 BTC) — целочисленный объём отклонял бы реальные биржевые выгрузки; молчаливое округление данных запрещено.
- **Альтернативы**: масштабирование до «сатоши»-целых — отклонено: усложняет контракт без необходимости (объём используется только в признаках и отчётах, не в заявках).
- **Последствия**: агрегация volume=sum работает с float; признак объёма не меняет semantics.

## D14. Количество в заявках: целые единицы; дробные количества отложены

- **Решение**: текущая схема (`instrument.lot_size_units`, `quantity_units`) оперирует ЦЕЛЫМИ единицами базового актива. Дробные количества (биржевые stepSize вроде 0.00001 BTC), точность Decimal для quantity — отложены до реализации биржевого адаптера.
- **Статус**: отложено (осознанное ограничение TEST-контура).
- **Аргументы**: в TEST-симуляции целые единицы с явным `lot_size_units` достаточны и безопасны; менять контракт количества без реальной биржевой специфики — преждевременно.
- **Последствия**: LIVE-адаптер обязан решить вопрос дробных количеств ЯВНО (D15-чек-лист) до первых заявок.

## D15. Тип рынка НЕ предполагается: спот / маржа / фьючерсы — отложенное решение

- **Решение**: проект НЕ предполагает поддержку спота, маржинальной торговли или фьючерсов по умолчанию. Текущий TEST-симулятор моделирует long-only покупку/продажу без плеча, займа и funding — это упрощённая модель, а не заявление о поддержке рынка. Реальный тип рынка, валюта маржи, плечо, режим хеджирования, funding-платежи фиксируются отдельно при подключении конкретной биржи.
- **Статус**: отложено до этапа E2/E3 (roadmap).
- **Аргументы**: экономка маржи/фьючерсов (ликвидации, funding, кросс/изолированная маржа) не моделируется симулятором — молча «поддерживать» их было бы обманом; спот-специфика (например, dust-остатки) тоже требует биржевых деталей.
- **Последствия**: `risk.allow_short: false` и отсутствие плеча — консервативная граница; любые расширения — только через явные конфиги, документацию и тесты.

## D16. Статус системы

- **Решение**: система — исследовательский TEST-контур на локальных CSV. Она **не** production-ready, LIVE-торговля невозможна (D8), доходность **не** обещается; все торгово-финансовые результаты — диагностические.
- **Статус**: принято.
