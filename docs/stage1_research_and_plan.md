### 2.3. Воспроизводимость исходного результата

**Невоспроизводим точно.** Причины:
1. Оба датасета отсутствуют в репозитории (абсолютные пути на машину автора).
2. Дневная модель требует внешних признаков (blockchain.com, Google Trends, золото) — их состав и состояние на дату обучения неизвестны.
3. Нет фиксированных random seed, сохранённых моделей и версий библиотек.
4. Ноутбуки не запускаются в современных окружениях: `from pandas import datetime`, `pandas.tools.plotting` (удалены в pandas ≥ 1.0), `statsmodels.tsa.arima_model` (удалён в statsmodels ≥ 0.13).
5. Метрики из README — заявления автора; считать их доказательством качества нельзя (плюс утечка scaler в дневной модели).

**Что сохраняем из подхода (для 5-мин модели):** признаки = сырые OHLCV(+turnover), цель = знак изменения close следующего бара (±1, ничья → −1 как в оригинале), хронологический сплит, XGBoost как основной алгоритм, набор метрик accuracy/f1/precision/recall + confusion matrix.

**Минимальные необходимые изменения:**
- Источник данных: CSV автора → публичный REST Bybit (свежие свечи BTCUSDT).
- Убрать последнюю строку (цель `shift(-1)` для неё не определена — в оригинале она молча получала метку −1 через сравнение с NaN).
- Единственный сплит → хронологическая walk-forward-валидация с **embargo** (последний бар тренировочного окна имеет метку, использующую close первого тестового бара → сдвиг границы на 1 бар устраняет утечку).
- Оригинал не даёт HOLD/уверенности → добавляем: уверенность = max(predict_proba), HOLD/воздержание при уверенности ниже порога из конфига (порог — настраиваемый, по умолчанию консервативный). Это правило уровня конфигурации, а не «выдуманные» уровни SL/TP.
- Фиксируем random seed, сохраняем артефакт + метаданные (версия, окно обучения, признаки, метрики).

### 2.4. Выбор инструмента и таймфрейма

- **Инструмент: BTCUSDT, category=spot** (по умолчанию задачи; причин менять не найдено).
- **Таймфрейм: 5 минут** — веская причина: только 5-минутный ноутбук использует признаки, которые Bybit отдаёт напрямую и в реальном времени (OHLCV). ## 3. Документация Bybit V5 (изучено + проверено эмпирически 2026-10-21)

### 3.1. REST GET /v5/market/kline
- Параметры: `category` (spot/linear/inverse; **default = linear → spot передавать явно**), `symbol` (обяз., uppercase), `interval` (обяз.; `5` доступно), `start`/`end` (мс), `limit` ∈ [1, 1000], default 200.
- Ответ `result.list`: массив строк `[startTime, open, high, low, close, volume, turnover]`, **отсортирован по убыванию startTime (новые первые)**. Для spot: volume в BTC, turnover в USDT.
- `close` незакрытой свечи = цена последней сделки → незакрытый бар надо определять (`startTime + interval > now`) и исключать из обучения/сигналов.
- Пагинация: при заданном `start` **без `end`** сервер возвращает до `limit` свечей вперёд от start. **Важно (эмпирически): при передаче и `start`, и `end` сервер возвращает самые СВЕЖИЕ `limit` свечей окна (от конца)** → пагинировать нужно запросами только со `start`, фильтруя `end` на клиенте. Первая свеча может начинаться чуть раньше `start` (сервер возвращает свечу, содержащую момент `start`).
- Глубина истории: 5-мин BTCUSDT spot доступен **минимум с 2021-10-01** (эмпирически; ~5 лет ≈ 525 тыс. баров ≈ 525 запросов по 1000). Фактическая загрузка 2024-01-01 → 2026-10-21: 296 страниц, 295 121 бар, ~110 с, 0 пропусков.
- `/v5/market/time`: серверное время в `result.timeSecond`/`timeNano` и top-level `time` (мс).
- Лимиты: публичные market-endpoint'ы не имеют per-UID лимита; действует **IP-лимит 600 запросов / 5 с**, при превышении — 403 и бан ~10 минут. План: троттлинг ~3 req/s + retry с экспоненциальным backoff на 429/403/5xx.

### 3.2. WebSocket public
- Spot mainnet: `wss://stream.bybit.com/v5/public/spot`; testnet: `wss://stream-testnet.bybit.com/v5/public/spot`. Публичные топики **без аутентификации**.
- Подписка: `{"op":"subscribe","args":["kline.5.BTCUSDT","tickers.BTCUSDT"],"req_id":...}` → ack `{"success":true,"ret_msg":"subscribe"}`. Для spot ≤ 10 args на запрос подписки.
- Kline-сообщение: `data[] = {start, end, interval, open, high, low, close, volume, turnover, confirm, timestamp}`, `type=snapshot`. **Закрытие свечи определяется полем `confirm=true`** (иначе бар ещё формируется). Частота пушей 1–60 с (эмпирически для BTC ≈ каждые ~2 с).
- Ticker spot (`tickers.BTCUSDT`): `lastPrice`, `highPrice24h`, `volume24h` и т.д. — для живого отображения цены (эмпирически ~2 сообщения/с).
- Heartbeat: отправлять `{"op":"ping"}` **каждые 20 с**; при отсутствии трафика сервер рвёт соединение (~10 мин). Требуется reconnect с backoff; IP-лимит: ≤ 500 соединений / 5 мин, не частить connect/disconnect, ≤ 1000 market-data соединений на IP.
- Эмпирическая проверка из песочницы выполнена: подписка, ~15 kline-сообщений и ~57 ticker-сообщений за 30 с, `confirm=false` на открытом баре — всё соответствует документации.

Ключевые решения:
- Общий интерфейс `MarketDataSource` — добавление другой биржи = новый класс без изменения бота.
- Сигнал формируется **только по закрытому бару** (`confirm=true` из WS либо бар с `start+interval ≤ now` из REST).
- Freshness-gate: если `now - last_update > N * interval` или соединение потеряно → статус STALE/DISCONNECTED, новый сигнал не выдаётся, рекомендации по позиции не выдаются.
- Журнал (сигналы + позиции) — атомарная запись в JSON, переживает перезапуск.
- Никаких приватных API, ордеров, балансов, API-ключей. Только публичные данные.

## 6. Риски

1. **Качество модели**: предсказание знака следующего 5-мин бара — заведомо слабая задача (базовая точность ~50–53%). Accuracy выше baseline не означает прибыльность (не учитываются спред/комиссии/слиппедж). Будет явно указано в отчёте и README.
2. **Дрейф**: сырые уровни цен как признаки (наследие оригинала) устаревают при смене ценового диапазона → walk-forward-переобучение обязательно; в live модель помечается версией и датой обучения, рекомендуется периодическое переобучение вручную.
3. **Сетевые сбои песочницы/пользователя**: live-проверки могут падать из-за сети → все manual checks имеют офлайн-режим (реплей записанных данных) как основной, live — опциональный флаг.
4. **pandas 3.x** в песочнице: код пишется совместимо с pandas 2.2+ и 3.x; версии закрепляются в requirements.txt.
5. **WS-лимиты**: reconnect с backoff ≥ 1 с, не более нескольких попыток в минуту — в пределах 500 conn/5 min.
6. **Незакрытые свечи и пропуски**: явная обработка и логирование; фабрикация данных запрещена — пропуски остаются пропусками (в отчёте gaps count).
7. **Отсутствие «текущего проекта»**: структура может измениться, если пользователь предоставит существующий бот.

## 7. Ограничения (фиксируются сразу)

- Сигналы — вывод статистической модели, не гарантия дохода и не индивидуальная финансовая рекомендация.
- Бот не знает фактических позиций пользователя без ручной регистрации; SELL для spot BTCUSDT трактуется только как «закрыть/уменьшить длинную позицию», короткие позиции не открываются.
- Стоп-лоссы/тейк-профиты/сроки удержания не изобретаются — только явно заданные в конфиге правила выходов; если их нет — бот воздерживается от рекомендаций по управлению позицией.
- Автоматическое переобучение на результатах позиций запрещено.
