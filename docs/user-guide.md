# Простое руководство по tradebot (для новичка, крипторежим)

Этот текст написан максимально простым языком. Если вы раньше не торговали и не
программировали — начните отсюда. Технические детали — в
[user_guide.md](user_guide.md) и остальных документах `docs/`.

---

## О чём этот проект и чего он НЕ делает

**Делает:** помогает исследовать идею торговой стратегии на криптовалютах —
загрузить исторические свечи из CSV-файлов, посчитать признаки, обучить модель
(LightGBM), прогнать «симуляцию торговли» на истории с комиссиями, слиппеджем и
риск-лимитами, и получить отчёт + журнал каждого решения.

**НЕ делает (важно!):**
- **не торгует по-настоящему.** Подключение к криптобирже НЕ реализовано:
  программа физически не умеет отправлять заявки, у неё нет сетевых запросов;
- LIVE-режим заблокирован «многофакторным гейтом» — даже если очень захотеть и
  включить все флаги, ордера невозможны (подробнее — раздел 8);
- **не обещает прибыль.** Результаты симуляции — диагностические: они показывают,
  как стратегия вела бы себя на истории при ВАШИХ допущениях, а не гарантируют
  будущий доход. Большинство «красивых» результатов на истории — следствие
  подгонки или утечек данных; проект как раз защищает от самообмана.

## Словарь простыми словами

- **Свеча (бар, OHLCV)** — запись о цене за интервал: время начала, цена
  открытия (Open), максимум (High), минимум (Low), цена закрытия (Close) и
  объём (Volume) — сколько актива наторговали.
- **Таймфрейм** — длительность интервала свечи: 1m (минута), 5m, 10m, 15m, 1h.
- **UTC** — всемирное время без летних/зимних переводов. Криптобиржи отдают
  свечи в UTC; проект хранит всё время в UTC — так метки однозначны.
- **Рынок 24/7** — криптовалюты торгуются круглосуточно без выходных, поэтому
  «торговый календарь» проекта по умолчанию покрывает все дни и часы.
- **Признак (фича)** — число, которое модель видит на каждом баре: например
  доходность за прошлый бар, RSI, объём относительно среднего. Все признаки
  «причинные» — используют только прошлое, не будущее.
- **Метка** — что считаем «правильным ответом» для обучения: например, выросла
  ли цена через N баров сильнее издержек.
- **Walk-forward** — честная схема проверки: обучаемся на прошлом, проверяем на
  следующем отрезке, двигаемся вперёд. Никакого «обучения на экзамене».
- **Симулятор (TEST)** — «игра в биржу» на истории: заявки исполняются по
  правилам (открытие следующего бара ± слиппедж), комиссии вычитаются, лимиты
  риска соблюдаются. Реальных денег нет.
- **Слиппедж (проскальзывание)** — разница между ожидаемой и фактической ценой
  сделки. В симуляции — ваше явное допущение в базисных пунктах (б.п., 1 б.п. = 0.01%).
- **Риск-лимиты** — правила «стоп-крана»: максимальная позиция, убыток на день,
  просадка и т.д. Нарушение — отказ от сделки или полная остановка.
- **Журнал (JSONL)** — файл, где построчно записано каждое решение: сигнал,
  проверка риска, исполнение. Для аудита «почему так произошло».
- **LIVE-гейт** — набор блокираторов реальных заявок. Сейчас главный блокиратор:
  биржевой адаптер не реализован, поэтому LIVE невозможен в принципе.

## 1. Установка

Нужен Python 3.10 или новее (проверка: `python --version`). Все команды — в
PowerShell (Windows) из корня папки проекта.

```powershell
python -m pip install -e ".[dev,ml]"
```

Что поставилось: сам проект (`tradebot`), библиотеки для конфигов (pydantic,
PyYAML), для ML (numpy, pandas, lightgbm, scikit-learn, pyarrow) и pytest для
тестов. Сетевых/биржевых библиотек нет — они проекту не нужны.

Проверка установки:

```powershell
python -m pytest
```

Ожидается строка вида `288 passed, 1 skipped` (числа могут отличаться — важно,
чтобы не было `failed`).

Если LightGBM не импортируется на Linux — доустановите системный пакет
`libgomp1`. Предупреждения OpenBLAS в выводе безвредны.

## 2. Первый запуск — без интернета и без своих данных

В проекте есть **демонстрационные данные**: `data\demo\DEMO_M1.csv`. Это
СИНТЕТИКА (искусственные свечи с простым линейным шаблоном), а не реальный
рынок — они нужны только чтобы всё «пощупать».

```powershell
# 1) проверить демо-данные и агрегацию таймфреймов
python -m tradebot.cli.validate_data --config configs\demo.yaml --resample 10m

# 2) прогнать сценарий проверки крипторежима (офлайн, ~1-2 минуты)
python scripts\manual_checks\check_crypto_mode.py
# ожидаемый итог: RESULT: PASS (12/12 checks)

# 3) полный TEST-прогон с обучением модели на демо-конфиге
python -m tradebot test --config configs\sim_demo.yaml --timeframe 5m --train
```

Последняя команда напечатает шаги `[1/5] ... [5/5]`, итог по капиталу, комиссиям
и сделкам, пути к отчёту и журналу, и фразу «Реальные заявки не выставлялись».
Цифры на синтетике бессмысленны как «доходность» — смысл в том, что пайплайн
работает от начала до конца. Примечание: на линейной демо-серии входов может
быть ноль (движения не превышают нейтральную полосу издержек) — это нормальное,
честное поведение; прогон со сделками показывают сценарии
`check_phase_05_test_run.py` и `check_crypto_mode.py` (там синтетика с режимами
дрейфа и волатильности).

## 3. Как подготовить CSV с историческими данными

### 3.1. Формат файла — строго такой

```
datetime,open,high,low,close,volume
2024-01-03 18:00:00,42150.50,42210.00,42100.10,42180.20,123.456
```

- ровно эти 6 колонок (порядок может быть любым, лишние колонки — ошибка);
- разделитель чисел — точка (запятая сломает разбор);
- время — `ГГГГ-ММ-ДД ЧЧ:ММ:СС` в UTC (или ISO-8601 со смещением, например
  `2024-01-03T18:00:00+00:00`);
- объём может быть дробным (для крипто это нормально — объём в BTC и т.п.);
- свечи должны идти строго по возрастанию времени, без дубликатов, и лежать на
  сетке таймфрейма (00, 05, 10... минут для 5m).

Программа НЕ «чинит» данные молча: любой дефект — понятная ошибка с номером
строки. Пропуски свечей — предупреждение (бары не выдумываются).

### 3.2. Где взять данные и куда положить

Скачайте исторические свечи у своей биржи (многие отдают CSV/ZIP, например
выгрузки klines). Положите файлы в `data\raw\`, например:

```
data\raw\BTCUSDT_M1.csv
data\raw\BTCUSDT_M5.csv
```

Достаточно ОДНОГО базового файла (1m или 5m): остальные таймфреймы проект
построит сам ресэмплингом (10m всегда строится из 5m/1m — нативных 10-минутных
свечей у бирж обычно нет).

### 3.3. Два параметра, которые нужно подтвердить самому

1. **Семантика метки** (`timestamp_semantics`): время в строке — это НАЧАЛО
   свечи (`bar_open`, самый частый вариант) или её КОНЕЦ (`bar_close`)?
   Посмотрите в документации вашей выгрузки. Ошибка здесь сдвигает все сигналы
   на бар — это критично.
2. **Таймзона** (`source_timezone`): почти всегда `UTC`. Если ваша выгрузка в
   локальном времени — укажите её зону (например `Asia/Almaty`), программа
   переведёт всё в UTC сама.

И **объём** (`volume_units`): в базовом активе (`base_asset`, стандарт) или в
USDT (`quote_asset`) — тоже смотрите в документации выгрузки.

### 3.4. Сколько нужно данных для обучения

Минимум определяется конфигом: `lookback_bars` (окно признаков) +
`horizon_bars` (горизонт метки) + требования walk-forward-валидации
(`min_train_bars`, по умолчанию 1000, и `min_val_bars`). Практический ориентир:
для 5m-стратегии — от нескольких десятков тысяч баров (недели-месяцы истории);
чем больше, тем достовернее оценка. На короткой истории запуск честно
откажется с кодом 3 («недостаточно истории»).

### 3.5. Проверка файла перед использованием

```powershell
# через ваш конфиг (проверит все файлы, перечисленные в нём):
python -m tradebot.cli.validate_data --config configs\my.yaml

# или один файл без конфига (--timeframe и --timestamp-semantics обязательны):
python -m tradebot.cli.validate_data --csv data\raw\BTCUSDT_M5.csv --timeframe 5m --timestamp-semantics bar_open
```

Итог `ИТОГ: OK` (предупреждения о пропусках допустимы и показываются отдельно).

## 4. Конфигурация: таймфрейм и режим TEST

Скопируйте пример и отредактируйте:

```powershell
Copy-Item configs\test_pipeline_example.yaml configs\my.yaml
```

Ключевые поля:

- `run.mode: TEST` — единственный рабочий режим (LIVE отклоняется);
- `run.experiment_id` — имя прогона (попадает в имена отчётов/модели);
- `data.symbols[].ticker` — пара, например `BTCUSDT`; `files` — ваши CSV;
- `timeframes` — для каждого включённого таймфрейма ОБЯЗАТЕЛЬНЫ
  `lookback_bars` и `horizon_bars` (без них конфиг не загрузится — так
  задумано: никаких молчаливых значений «по умолчанию» для стратегии);
- `sessions` — для крипто оставьте 24/7 (как в примере) или удалите секцию;
- `risk` и `simulation` — капитал, лимиты, комиссии, слиппедж. Это ВАШИ ЯВНЫЕ
  допущения: без них симуляция безопасно отказывается стартовать. Реальные
  комиссии возьмите из тарифов своей биржи (спот-торговля, например, обычно
  считается в б.п. от оборота).

Опечатка в конфиге = ошибка загрузки (схема строгая) — это защита, а не баг.

## 5. Запуск обучения и бэктеста

```powershell
# всё сразу: обучение + симуляция + отчёт + журнал
python -m tradebot test --config configs\my.yaml --timeframe 5m --train

# повторить бэктест с уже обученной моделью (без переобучения):
python -m tradebot test --config configs\my.yaml --timeframe 5m --model-dir models\<артефакт>

# только обучение (без симуляции):
python -m tradebot.cli.train --config configs\my.yaml --timeframe 5m

# только симуляция с готовой моделью:
python -m tradebot.cli.simulate --config configs\my.yaml --timeframe 5m --model-dir models\<артефакт>
```

Коды возврата: 0 — успех; 2 — проблема в конфигурации; 3 — мало истории;
4 — ошибка данных/модели/симуляции. Сообщения об ошибках печатаются на русском
и объясняют, что исправить.

## 6. Результаты: где смотреть и как понимать

После прогона создаются (пути напечатает команда):

- `reports\test_run_<experiment>_<tf>.md` — отчёт симуляции;
- `reports\journal_<experiment>_<tf>.jsonl` — журнал решений (построчно JSON);
- `models\<experiment>_<tf>_<hash>\` — артефакт модели (LightGBM + метаданные +
  манифест признаков);
- `reports\train_report_*.md` — отчёт обучения (если было `--train`).

Каталоги `reports\` и `models\` исключены из git.

### 6.1. Отчёт симуляции — раздел «Результаты»

- **net_return** — итоговая доходность ПОСЛЕ комиссий и слиппеджа (в долях);
- **max_drawdown** — максимальная просадка капитала от пика (насколько «больно»
  было бы по пути);
- **n_entries / n_round_trips** — сколько входов и завершённых сделок;
- **hit_rate / profit factor** — доля прибыльных сделок и отношение прибыли к
  убытку. Мало сделок — метрики ненадёжны;
- **total_commission** — сколько «съели» комиссии (на крипте это главный враг
  частых стратегий);
- **rejections** — сколько сигналов отклонил риск-контроль и почему.

### 6.2. Отчёт обучения

Смотрите **OOS-метрики** (out-of-sample, walk-forward): ROC-AUC выше 0.5 —
модель хоть что-то отличает от монетки; сравнение с базейнами («предыдущий
знак», логрег) обязательно: если бустинг их не обыгрывает — сигнала нет.
«Вердикт» — диагностический, по заранее зафиксированным порогам.

### 6.3. Как ко всему этому относиться

Хороший OOS-результат — НЕ сигнал «включать на деньги». Это повод: проверить
допущения (комиссии/слиппедж не занижены?), устойчивость (другие таймфреймы,
подпериоды), и понимать, что LIVE-исполнение всегда хуже симуляции. И главное:
реальная торговля в этом проекте сейчас невозможна технически.

## 7. Частые ошибки и как их исправить

| Симптом | Причина | Что делать |
|---|---|---|
| `E_HEADER_UNKNOWN_COLS` | лишняя колонка в CSV | оставьте ровно 6 колонок формата |
| `E_OFF_GRID` | метки не кратны таймфрейму | проверьте таймфрейм файла и семантику метки |
| `E_UNSORTED`/`E_DUPLICATE_TS` | строки не по порядку/дубли | исправьте выгрузку (бот не сортирует молча) |
| много `W_GAP` | пропуски свечей или неверный таймфрейм | сверьте источник; для 24/7 данных пропусков быть не должно |
| `ConfigError` про лишние поля | старый конфиг прежней версии | пересоберите конфиг из новых примеров |
| exit 2 «НЕПОЛНАЯ КОНФИГУРАЦИЯ» | нет risk/simulation или не заданы лимиты | заполните разделы явно (пример — configs\sim_demo.yaml) |
| exit 3 «НЕДОСТАТОЧНО ИСТОРИИ» | мало баров для walk-forward | дайте больше истории или уменьшите min_train_bars осознанно |
| `ModuleNotFoundError: lightgbm` | не установлен extra | `python -m pip install -e ".[ml]"` |

## 8. LIVE-режим: что нужно знать и как не отправить реальную заявку

### 8.1. Честный статус

LIVE **не реализован и недоступен**. В проекте нет: API-клиента биржи,
аутентификации, отправки ордеров, потоковых данных. Есть только:
- контракты (интерфейсы), которые будущий адаптер должен реализовать
  (`marketdata/`, `execution.BrokerGateway`, `exchange/`);
- многофакторный LIVE-гейт, который сейчас отказывает ВСЕГДА, потому что его
  условие №0 — «интеграция с биржей доступна» — ложно
  (`exchange.base.EXCHANGE_INTEGRATION_AVAILABLE = False`).

### 8.2. Почему случайная реальная заявка невозможна

1. отправлять нечего и некуда: сетевого кода в проекте нет (гигиенические
   тесты блокируют появление торговых эндпоинтов);
2. команда `test` отклоняет конфиг с `mode: LIVE`;
3. `live-preflight` даже с флагом `--allow-live`, env-подтверждением
   `TRADEBOT_LIVE_ACK=ENABLE-LIVE` и `live.allow_orders: true` завершается
   отказом (гейт перечисляет все причины, включая главную — отсутствие биржевой
   интеграции);
4. kill-switch-файл `.kill` дополнительно запрещает заявки (для будущего).

Когда LIVE станет возможным — это будет отдельная большая работа (этапы E1–E3 в
[roadmap.md](roadmap.md)) с проверками на тестнете и явным решением
пользователя; до тех пор любые заявления «бот торгует» — неправда.

### 8.3. Секреты (ключи API) — правила обращения

Сейчас ключи не нужны вовсе. На будущее правила уже заложены: только
переменные окружения или файл `.env` (он исключён из git; шаблон —
`.env.example`), маскирование значений в логах и журнале, никогда не в коде и
конфигах. Если вы где-то увидели просьбу вписать ключ в YAML — это баг,
сообщите о нём.

## 9. Краткий словарь

См. начало документа. Дополнительно: **эмбарго** — зазор между фолдами
валидации, чтобы перекрывающиеся метки не «протекали»; **нейтральная полоса** —
диапазон движения цены меньше издержек: такие бары не торгуются; **pending-бар**
— незакрытая свеча (решения по ней не принимаются); **reconciliation** — сверка
локального учёта позиций с биржевым (будущий LIVE); **kill-switch** — файл-
«стоп-кран» для заявок.
